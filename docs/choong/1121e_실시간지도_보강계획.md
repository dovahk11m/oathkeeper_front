# 1121e: 실시간 지도 기능 보강 계획

## 1. 개요

현재 실시간 지도 기능의 서버 측 기본 로직(위치 수신 -> 이벤트 발행 -> WebSocket 전송)은 구현되어 있으나, 사용자 경험을 향상시키고 기획 의도를 충족시키기 위한 고급 기능(약속 페이즈 연동, GPS 미변화 감지, 자동 도착 처리, 실시간 위치 캐싱)은 추가 구현이 필요함. 이 문서는 해당 기능들의 구현 계획을 상세히 기술함.

## 2. 주요 목표

-   약속 상태에 따른 실시간 위치 추적 로직의 동적 활성화/비활성화 구현.
-   사용자의 GPS 위치 변화가 없을 때 이를 감지하고 알림을 제공하는 시스템 구축.
-   약속 장소 근처 도달 시 자동으로 도착을 처리하는 기능 구현.
-   실시간 위치 데이터의 효율적인 캐싱 및 빠른 조회를 위한 인메모리 맵 연동.

## 3. 세부 구현 계획

### 3.1. 인메모리 맵 설정 및 `TrackService`에 연동 (Redis 대체)

-   **목표:** 실시간 위치 데이터의 빠른 접근 및 캐싱 기반 마련 (Redis 없이).
-   **수정 파일:**
    -   `com.oath.domain.locationevents.service.TrackService.java`: `RedisTemplate` 대신 `ConcurrentHashMap` 주입.
-   **구현 내용:**
    -   `TrackService` 내에서 `RedisTemplate` 의존성을 제거하고, `ConcurrentHashMap`을 사용하여 `realtimeLocationCache`와 `stationaryCheckCache`를 정의.
    -   Redis 관련 `putAll`, `entries`, `delete` 호출을 `ConcurrentHashMap` 관련 메서드(put, getOrDefault, remove)로 변경.
    -   `src/main/resources/application-local.yml`에서 Redis 설정 제거.

### 3.2. 약속 페이즈 연동 로직 구현

-   **목표:** 약속 상태에 따른 위치 추적 기능의 활성화/비활성화 제어.
-   **수정 파일:**
    -   `com.oath.domain.locationevents.service.TrackService.java`
-   **구현 내용:**
    -   `TrackService`에 `com.oath.domain.plan.repository.PlanRepository` 또는 `com.oath.domain.plan.service.PlanService` 주입.
    -   `storeTracks` 메서드 내에서 `participantId`를 통해 `planId`를 얻고, `PlanRepository`를 통해 약속의 현재 상태(예: `Status.IN_PROGRESS`, `Status.CONFIRMED`)를 조회.
    -   조회된 약속 상태가 '이동 중' 또는 '진행 중'과 같이 실시간 위치 추적이 필요한 페이즈일 때만 GPS 미변화 감지, 자동 도착 처리 등의 고급 로직이 동작하도록 조건부 처리.

### 3.3. GPS 미변화 감지 기능 구현

-   **목표:** 사용자의 GPS 미변화 상황을 감지하고 알림을 제공.
-   **신규 파일:**
    -   `com.oath.domain.locationevents.event.GpsStationaryEvent.java`
    -   `com.oath.domain.locationevents.event.listener.GpsStationaryListener.java`
-   **수정 파일:**
    -   `src/main/resources/application-local.yml`: `notification.policy.on-gps-stationary: EMAIL` 정책 추가.
    -   `com.oath.domain.locationevents.service.TrackService.java`: `detectGpsStationary` 메서드 추가 및 `storeTracks`에서 호출.
-   **구현 내용:**
    -   **`GpsStationaryEvent`**: `planId`, `participantId`, `memberId`, `username`, `lastKnownLocation`, `stationaryStartTime`, `stationaryDurationMinutes`를 포함하는 이벤트 클래스 정의.
    -   **`TrackService`**:
        -   인메모리 맵에 저장된 각 `participantId`의 이전 위치 정보와 현재 수신된 위치 정보를 비교.
        -   일정 시간(예: 5분) 동안 GPS 좌표 변화가 거의 없음을 감지 시 `GpsStationaryEvent` 발행. (이벤트 발행 전 인메모리 맵에 마지막 감지 시간 기록)
    -   **`GpsStationaryListener`**:
        -   `GpsStationaryEvent`를 수신.
        -   `com.oath.domain.alarms.AlarmFactory`를 통해 사용자에게 '아직 출발 준비 중인가요?'와 같은 알림 발송. (알림 중복 방지 로직 고려)

### 3.4. 자동 도착 처리 기능 구현

-   **목표:** 약속 장소 근처 도달 시 자동 도착 처리 및 후속 작업 트리거.
-   **신규 파일:**
    -   `com.oath.domain.locationevents.event.ParticipantArrivedEvent.java`
    -   `com.oath.domain.locationevents.event.listener.ParticipantArrivedListener.java`
-   **수정 파일:**
    -   `com.oath.domain.locationevents.service.TrackService.java`
    -   `com.oath.domain.plan.service.PlanService.java` (참가자 도착 상태 업데이트 메서드 추가 또는 수정)
-   **구현 내용:**
    -   **`TrackService`**:
        -   `PlanRepository`를 주입받아 해당 `planId`의 약속 장소 좌표(`placeLatitude`, `placeLongitude`) 조회.
        -   수신된 `TrackPointReq`의 위치가 약속 장소의 특정 반경(예: 100m) 내에 들어왔는지 계산.
        -   조건 충족 시 `ParticipantArrivedEvent` 발행.
    -   **`ParticipantArrivedEvent`**: `planId`, `participantId`, `memberId`, `username`, `arrivalLocation`, `arrivalTime` 등을 포함하는 이벤트 클래스 정의.
    -   **`ParticipantArrivedListener`**: `ParticipantArrivedEvent`를 수신하여 `PlanService.updateParticipantArrivalStatus`를 호출하여 참가자의 `MovementStatus`를 `ARRIVED`로 변경하고, 도착 시간 및 지각 여부 계산, 관련 이벤트 발행, 약속 자동 완료 체크 로직 수행.

### 3.5. 클라이언트 이벤트 WebSocket 알림 구현

-   **목표:** `GpsStationaryEvent` 및 `ParticipantArrivedEvent`를 클라이언트가 구독하는 별도 WebSocket 채널로 전송.
-   **신규 파일:**
    -   `com.oath.domain.locationevents.dto.GpsStationaryNotificationDto.java`
    -   `com.oath.domain.locationevents.dto.ParticipantArrivedNotificationDto.java`
-   **수정 파일:**
    -   `com.oath.domain.locationevents.event.listener.GpsStationaryListener.java`
    -   `com.oath.domain.locationevents.event.listener.ParticipantArrivedListener.java`
-   **구현 내용:**
    -   **`GpsStationaryNotificationDto` 및 `ParticipantArrivedNotificationDto`**: 클라이언트가 WebSocket 메시지를 수신했을 때 파싱할 수 있는 형태로 이벤트 정보를 담는 DTO 정의.
    -   **`GpsStationaryListener` 및 `ParticipantArrivedListener`**:
        -   `SimpMessagingTemplate`을 주입받음.
        -   이벤트 발생 시, 해당 이벤트를 적절한 Notification DTO로 변환.
        -   `messagingTemplate.convertAndSend("/topic/plans/{planId}/events", notificationDto)`를 사용하여 클라이언트가 선호하는 별도 채널로 메시지 전송.

## 4. 향후 고려 사항

-   `TrackService`의 책임이 과도하게 커질 경우, `LocationProcessingService`와 같이 세분화된 서비스로 책임을 분리하는 리팩토링 고려.
-   인메모리 캐싱의 한계 (애플리케이션 재시작 시 데이터 유실, 스케일 아웃 시 데이터 불일치) 고려 및 Redis 또는 영속성 있는 캐싱 솔루션 도입 검토.
-   클라이언트와의 통합 테스트 시나리오에 엣지 케이스(네트워크 불안정, 앱 백그라운드 전환 등) 추가.

## 5. 클라이언트(Flutter) 개발팀 요청 사항

서버 작업 시 클라이언트 연동을 위해 다음 사항들을 고려해 주시기 바랍니다.

### 5.1. 약속 상태(Phase) 동기화 API
- **요청:** 실시간 지도 진입 시 현재 약속의 상태(`READY`, `MOVING`, `ARRIVED` 등)를 알 수 있는 필드가 `PlanDto` 또는 별도 API에 포함되어야 합니다.
- **이유:** 약속 상태에 따라 위치 공유 자동 시작/중지 및 UI 표시(예: "이동 중", "도착")를 분기처리하기 위함입니다.

### 5.2. 이벤트 수신 채널 일원화 또는 분리 명세
- **요청:** `GpsStationaryEvent`, `ParticipantArrivedEvent` 등의 알림이 어떤 STOMP 경로로 오는지 확정 필요합니다.
    - **안 1:** 기존 `/topic/room/{planId}`로 통합 (메시지 타입으로 구분: `LOCATION`, `EVENT`)
    - **안 2:** 별도 채널 `/topic/plans/{planId}/events` 사용
- **선호:** 메시지 파싱 복잡도를 낮추기 위해 **안 2(별도 채널)**를 선호합니다.

### 5.3. 도착 판정 기준 공유
- **요청:** 서버에서 도착으로 판정하는 반경(예: 100m)과 클라이언트에서 시각적으로 "도착"으로 표시할 기준을 맞춰야 합니다.
- **질문:** 서버에서 도착 판정 시 `status`가 즉시 변경되나요? 아니면 클라이언트가 별도 이벤트를 수신해야 하나요?

### 5.4. 테스트용 강제 이벤트 트리거 API
- **요청:** 개발 중 실제 이동 없이도 "도착", "정체" 이벤트를 테스트할 수 있도록, 특정 멤버의 상태를 강제로 변경하거나 이벤트를 발생시키는 Admin/Dev API가 있으면 좋겠습니다.
