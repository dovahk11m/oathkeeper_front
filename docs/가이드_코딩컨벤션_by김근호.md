# Oath 프로젝트 코딩 규칙 및 모범 사례

이 문서는 Oath 프로젝트의 코드 품질, 일관성, 유지보수성을 높이기 위해 모든 개발자가 준수해야 할 코딩 규칙과 설계 원칙을 정의합니다.

---

## 1. JPA & 데이터베이스

### 1.1. OSIV(Open Session In View) 비활성화
-   **규칙:** `spring.jpa.open-in-view` 설정은 `false`로 유지합니다.
-   **근거:** OSIV를 켜면 DB 커넥션을 너무 오래 점유하여 커넥션 풀 고갈의 원인이 될 수 있습니다. 모든 DB 조회는 트랜잭션 안에서 완료하는 것을 원칙으로 합니다.

### 1.2. 지연 로딩(LAZY) 우선 사용
-   **규칙:** 모든 연관관계 매핑(`@ManyToOne`, `@OneToMany` 등)은 `fetch = FetchType.LAZY`로 설정하는 것을 기본으로 합니다.
-   **근거:** 즉시 로딩(EAGER)은 불필요한 연관 엔티티까지 조회하여 성능을 저하시키고, N+1 문제를 유발하기 쉽습니다. 필요한 연관 엔티티는 JPQL의 `join fetch`를 사용하여 명시적으로 함께 조회합니다.

### 1.3. N+1 문제 해결 (Fetch Join 및 Batch Size)
-   **규칙:** 연관된 엔티티를 함께 조회해야 할 경우, JPQL에서 `join fetch`를 우선적으로 사용합니다. 컬렉션 조회 등 `join fetch`를 사용하기 어려운 경우에는 `default_batch_fetch_size` 옵션을 활용합니다.
-   **근거:** N+1 문제는 애플리케이션의 성능을 심각하게 저하시키는 주요 원인입니다. 이를 방지하기 위해 데이터 조회 시 연관관계 로딩 전략을 항상 고려해야 합니다.

### 1.4. 양방향/단방향 및 Cascade 설정
-   **규칙:** 엔티티 간의 연관관계는 가급적 단방향으로 설계하고, 꼭 필요한 경우에만 양방향 관계를 설정합니다. `CascadeType.ALL`과 `orphanRemoval=true`는 부모 엔티티가 자식 엔티티의 생명주기를 완전히 관리할 때만 신중하게 사용합니다.
-   **근거:** 무분별한 양방향 관계와 Cascade 설정은 엔티티 간의 결합도를 높이고, 예상치 못한 데이터 삭제나 상태 변경을 유발할 수 있습니다.

## 2. DTO 및 엔티티 설계

### 2.1. DTO는 Static Inner Class로 관리
-   **규칙:** 요청(Request)과 응답(Response)에 사용되는 DTO는 관련된 도메인 클래스 내부에 `public static class`로 정의합니다. (예: `MemberResponse.Login`, `MemberRequest.Update`)
-   **근거:** 관련된 DTO들이 하나의 파일 안에서 관리되어 응집도가 높아지고, 코드 탐색이 용이해집니다.

### 2.2. 엔티티와 DTO의 역할 분리
-   **규칙:** 엔티티 클래스 내부에 DTO를 반환하는 메서드를 만들지 않습니다. DTO 변환의 책임은 DTO 자신이나 서비스 계층에 둡니다.
-   **근거:** 엔티티는 순수한 데이터 모델의 역할을 유지해야 합니다. 엔티티가 특정 DTO에 의존하게 되면, 표현 계층의 변경이 데이터 계층까지 영향을 미쳐 결합도가 높아집니다.

### 2.3. 정적 팩토리 메서드(Static Factory Method) 활용
-   **규칙:** DTO 객체를 생성할 때는 생성자 대신 `of()`, `from()`과 같은 목적이 명확한 정적 팩토리 메서드를 사용하는 것을 권장합니다.
-   **근거:** 생성자의 역할을 명확히 하고, 객체 생성 로직을 캡슐화하여 가독성과 재사용성을 높일 수 있습니다.

### 2.4. 빌더 패턴(Builder Pattern) 적극 활용
-   **규칙:** 엔티티나 복잡한 DTO 객체를 생성할 때는 빌더 패턴을 적극적으로 사용합니다.
-   **근거:** 생성자에 비해 어떤 필드에 어떤 값이 설정되는지 명확하게 알 수 있어 가독성이 높고, 객체 생성의 유연성을 제공합니다.

### 2.5. 순환 참조 주의 (`@ToString` 등)
-   **규칙:** 양방향 연관관계가 설정된 엔티티에서 `@ToString`을 사용할 경우, 연관관계 필드 중 하나는 `exclude` 옵션을 사용하여 순환 참조를 반드시 방지해야 합니다.
-   **근거:** 순환 참조는 `StackOverflowError`를 유발하여 애플리케이션을 중단시킬 수 있습니다.

## 3. 서비스 및 아키텍처

### 3.1. 전략 패턴(Strategy Pattern) 및 팩토리 패턴(Factory Pattern) 활용
-   **규칙:** 유사하지만 동작 방식이 다른 로직 그룹(예: 소셜 로그인, 알림 발송)이 있다면, 전략 패턴 등을 활용하여 확장 가능하고 유지보수가 용이한 구조를 설계합니다.
-   **근거:** 새로운 기능(예: 새로운 소셜 로그인 추가)이 필요할 때, 기존 코드를 수정하는 대신 새로운 전략 클래스를 추가하는 것만으로 기능을 확장할 수 있습니다.

### 3.2. 스프링 이벤트(Spring Event) 활용
-   **규칙:** 특정 도메인의 핵심 트랜잭션과 직접적인 관련이 없는 후속 작업(예: 알림 발송, 통계 누적, 메일 발송)은 이벤트를 발행하여 처리합니다.
-   **근거:** 도메인 간의 결합도를 낮추고, 각 서비스의 책임을 명확하게 분리할 수 있습니다. (예: `PlanService`는 `NotificationService`를 직접 알 필요가 없음)

### 3.3. Early Return 패턴 활용
-   **규칙:** 복잡한 `if-else` 구조 대신, 메서드 초반에 예외적인 상황(validation 실패, null 체크 등)을 먼저 검사하고 `return`하여 코드를 조기에 종료시킵니다.
-   **근거:** 코드의 깊이(depth)를 줄여 가독성을 높이고, 주된 로직의 흐름을 파악하기 쉽게 만듭니다.

### 3.4. 메서드 참조 사용 자제
-   **규칙:** 람다(lambda) 표현식이 더 명확한 경우, 무분별한 메서드 참조(Method Reference) 사용을 지양합니다.
-   **근거:** 메서드 참조는 코드를 간결하게 만들지만, 어떤 메서드가 호출되는지 추적하기 어려워 디버깅을 방해하고 가독성을 해칠 수 있습니다.

## 4. API 및 공통 모듈

### 4.1. 공통 DTO 설계 (제네릭 활용)
-   **규칙:** 모든 API 응답은 `CommonResponse<T>`와 같이 제네릭을 활용한 공통 래퍼(Wrapper) 클래스를 사용하여 일관된 응답 형식을 유지합니다.
-   **근거:** 클라이언트가 API 응답을 파싱하고 처리하는 로직을 표준화할 수 있습니다.

### 4.2. 공통 예외 처리
-   **규칙:** 비즈니스 로직 상의 예외는 미리 정의된 `Exception4xx` 시리즈(예: `Exception404`)를 상속받아 구체적인 예외 클래스를 만들어 사용합니다. `@RestControllerAdvice`를 통해 공통으로 처리합니다.
-   **근거:** 예외 처리 로직의 중복을 막고, 일관된 형식의 오류 응답을 클라이언트에게 전달할 수 있습니다.

### 4.3. 인터셉터 및 CORS 설정
-   **규칙:** 인증/인가와 같이 여러 API에 공통적으로 적용되어야 하는 로직은 Spring Interceptor를 활용합니다. CORS(Cross-Origin Resource Sharing) 설정은 `WebConfig`에서 중앙 관리합니다.
-   **근거:** 컨트롤러의 책임과 횡단 관심사(cross-cutting concerns)를 분리하여 코드의 응집도를 높입니다.

### 4.4. JWT 토큰 사용
-   **규칙:** 사용자 인증은 상태를 저장하지 않는(stateless) JWT(JSON Web Token) 방식을 사용합니다.
-   **근거:** 서버의 확장성을 높이고, 다양한 클라이언트 환경(웹, 모바일)을 유연하게 지원할 수 있습니다.

## 5. 개발 환경 및 기타

### 5.1. 운영 환경 분리
-   **규칙:** 최소 `local`, `test`, `prod` 3개의 환경으로 분리하여 관리합니다. 각 환경의 설정은 `application-{profile}.yml` 파일을 통해 관리합니다.
-   **근거:** 각 환경에 맞는 DB 접속 정보, 외부 API 주소 등을 유연하게 변경하고, 개발 환경에서의 실수가 운영 환경에 영향을 미치는 것을 방지합니다.

### 5.2. `CommandLineRunner` 활용
-   **규칙:** 애플리케이션 시작 시점에 특정 데이터를 초기화하거나, 검증 로직을 수행해야 할 경우 `CommandLineRunner`를 활용합니다. (예: `DataInitializer`)
-   **근거:** 애플리케이션 구동 시점에 필요한 준비 작업을 체계적으로 관리할 수 있습니다.
